## Test corrections (after the RED run; documented in the files)
1. tCoreAxis/orientationInputsAgree (before any implementation): expected origin for `'Units', "ft"` written as `[1; 2; 3] * 0.3048` instead of the decimal literals `[0.3048; 0.6096; 0.9144]`: with tolerance 0 the literal 0.9144 is not the double 3 * 0.3048. Tolerance unchanged (0).
2. tCoreAxis/chainsResolveBothWays and /compositionMatchesSe3: the expected matrices contradicted the test's own pre-registered contract in its header (`a.dcmTo(b) = C_ba`): the test expected the product C_a_root for `a.dcmTo(root)`, which by that contract is C_root_a (its transpose); likewise for the se3 check. Corrected to the header's contract; the class was not changed to fit; tolerances unchanged.
3. tCorePointVector/crossDotNorm: `norm` tolerance 0 -> 1e-15 relative: `sqrt(sum(v.^2))` and MATLAB's `norm` differ by one ulp (1.8e-15 on 8.77).
4. tCorePerformance (changed after the first GREEN iteration, which measured 1.29 with the model asked for xdot only): both paths are now asked for `[xdot, y]`, because the plant always builds y; timing the model without y flattered it. This makes the comparison stricter, not looser; the 1.25 bound is unchanged. The ratio then came under 1.25 through D2 (no second engine evaluation) and D10/D13 (fewer dispatch layers), not through the test.
